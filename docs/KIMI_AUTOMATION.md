# Работа Kimi через GitHub Actions

Это отдельный способ работы от GitHub-плагина в чате Kimi. В чате Kimi ничего запускать не требуется.

## Перед первым рабочим заданием

- Workflow `.github/workflows/kimi-task.yml` и `scripts/kimi_pipeline.py` должны находиться в основной ветке репозитория, иначе события Issues и ручной запуск недоступны.
- Секрет репозитория: `KIMI_API_KEY`, созданный в Kimi Code. Endpoint зафиксирован: `https://api.kimi.com/coding/v1`; переключения на Moonshot API нет.
- В Settings → Actions → General → Workflow permissions включить **Allow GitHub Actions to create and approve pull requests**, если GitHub отклоняет создание PR. Одного `pull-requests: write` в YAML недостаточно при запрете на уровне настроек. Это разрешение используется для создания черновика; автоматического одобрения или слияния в workflow нет.
- Создать метку `kimi-run`, если её ещё нет. Ручной запуск через Actions не требует этой метки.

## Запуск задания

1. Создать GitHub Issue с готовым ТЗ. В отдельной строке указать исходную ветку, например:

   `Kimi-Base: codex/recover-kimi-0.5.19`

2. Владелец репозитория добавляет метку `kimi-run`. Для повторного запуска удалить и снова добавить метку.
3. Либо открыть Actions → **Kimi task** → **Run workflow**, ввести номер Issue и исходную ветку. Для проверки самой интеграции включить `smoke` и оставить номер Issue пустым.
4. Результат — ветка `kimi/task-НОМЕР-RUN_ID-ПОПЫТКА`, патч в артефакте `kimi-result-patch` и черновик PR.

Не выбирайте `main` автоматически: в текущем проекте новая версия приложения может находиться в отдельной рабочей ветке. Workflow фиксирует SHA выбранной ветки до запуска.

## Проверки и сохранность

Kimi CLI 2.5.2 работает в контейнере без GitHub-токена. Ключ Kimi передаётся только этому запуску. Затем результат сохраняется обычным Git-патчем с точным содержимым байтов, включая Unicode. При прерывании агента workflow пытается сохранить уже подготовленные изменения.

Допускаются изменения `app/`, `docs/`, `README.md`, `BUILD_CHECKS.md`, `BACKLOG.md`. Изменения workflow, скриптов инфраструктуры, AGENTS.md, символические ссылки и подмодули отклоняются. Такие задачи выполняются отдельно после проверки.

Отдельная среда без Kimi-ключа проверяет применимость патча. При изменении `app/` запускаются сборка APK, сборка тестового APK, модульные тесты и Lint. Результат сохраняется даже при ошибке проверок: PR остаётся черновиком с указанием статуса.

**Device-тесты не входят в этот workflow.** Перед приёмкой изменений приложения запустить существующий Android build на результирующей ветке. GitHub может запросить одобрение workflow для PR, созданного GITHUB_TOKEN; не считать отсутствие такого прогона успехом тестов.

Если GitHub запретил создание PR, ветка и патч уже сохранены. После изменения настройки повторить только задание `publish` через Re-run failed jobs. Автоматического слияния и изменения исходной ветки нет.

Лимиты: один запуск на одну задачу одновременно; контейнер агента до 1000 секунд, до 60 шагов, до 2 попыток шага, патч до 2 MB. Повторные запуски расходуют квоту Kimi; наличие квоты и условия подписки проверяются в аккаунте Kimi. Workflow не включает покупку дополнительной квоты.

## Роли чатов

Диагностика и написание ТЗ могут оставаться в отдельных чатах. Для запуска достаточно разместить готовое ТЗ в Issue и добавить метку или запустить Actions. Сам по себе этот workflow не связывает разные чаты и не обходит их лимиты.
